# Sush and Sush Nightly review — 1 October 2026

## Verdict

Sush has a useful product foundation: a local workspace for launching, monitoring and handing off existing agent CLIs. Stable project roots, capability discovery, a real Claude transcript bridge, account slots and offline storage are valuable. Quiet Nights gives that foundation a clearer project-first interface.

Reliability and product clarity need more attention than adding another dashboard. Identity ownership, pending process launches and session-specific UI data had concrete failures despite a passing baseline suite. The app also presents three different account concepts and several overlapping AI surfaces. Those distinctions are harder for a user to understand than they should be.

This review fixes verified defects and records the larger work separately. It does not claim that all possible bugs have been removed or that provider logins have been tested live.

## Verified defects and fixes

| Priority | Failure before this change | Fix and evidence |
|---|---|---|
| High | Claude startup awaits capability discovery. A concurrent launch can bypass the process cap or spawn twice for one tab; a closed tab or changed identity can still receive a late launch. | Reserve pending launches, deduplicate per tab and invalidate them on close/runtime replacement. Assert ownership after discovery and before spawn. Deferred-start tests cover cap, deduplication, close, sign-out, identity switch and replacement reservation. |
| High | OAuth exchange/refresh persists using whichever identity is active when the network request completes. Switching identities can place the previous user's token in the next user's vault. A late refresh can also resurrect a disconnected connection. | Capture identity and request epoch, verify them after network awaits and write only to the captured owner. Tests cover switch/cancel during exchange, switch/disconnect during refresh and a successful owned exchange. |
| Medium | Refreshing a default account's usage inherits the active alternate account overlay; `slotEnv(default)` contributes no override. The default row can report a different account's credentials or quota. | Build explicit probes from the base identity environment plus only the requested slot. Test exercises both provider config and HOME overlays. |
| Medium | An invalid new PIN is rejected after profile fields have mutated in memory. A later save can persist those rejected edits. | Validate the PIN before any mutation. Test checks live state and state after another save/reload. |
| Medium | Name uniqueness is checked before truncating names to 32 characters, allowing two stored identities with the same name. | Normalize to the stored length before checking uniqueness. Regression test covers a common 32-character prefix. |
| Medium | Thread state survives switching sessions; late asynchronous responses can replace the active view with an older read. | Key the Thread host by session and discard responses after unmount or supersession. Browser regression checks that pending reads show no prior transcript. |

## Product and UX criticism

### The central workflow is good; its presentation is fragmented

Project rail → session → terminal → changes/context is understandable. But Agent, Claude, Thread and Seducia are separate concepts in the pane metadata, and there are additional topbar/palette entry points. An ordinary user cannot infer whether they are opening a second conversation, inspecting the existing CLI, or asking an orchestrator to act.

Make the session the main object. Put its terminal and structured activity beside one another. Keep orchestration as a clearly named workspace action. Explain when a surface starts a separate provider request. The Claude transcript bridge already follows the right principle: show observed records rather than inventing conversation turns from terminal escape output.

### Account language needs a clearer contract

A Sush identity, a CLI account slot and a Provider Connect token are different things. The UI should state which one the user is changing and whether a running session is restarted. A successful provider-token test is also different from proof that a CLI session is authenticated using that token.

The current account label/usage hook reads the provider-wide selected account, not an account binding stored with each live tab. Existing PTYs retain their launch environment after the provider default changes. This is a follow-up design risk: the displayed account can describe the selected default rather than the running process. Persist launch-time identity/provider/slot metadata with every session and render account status from that binding.

### Nightly's release identity is unfinished

There is no independently runnable Nightly repository or release pipeline. The product documentation calls the core “solid” while startup and ownership bugs remain. Preserve the existing core contracts, but allow tested fixes. Treat Nightly as an explicit release channel with a pinned source commit and known limitations until distribution packaging exists.

### The feature surface is too broad for its onboarding

The inspector metadata lists 18 tools across AI, project, web and operations. Seven plan tiers add another decision layer; developer workflows are not even enabled monotonically across every higher tier. The main interface should help a new user complete one task before presenting the whole toolbox.

Default onboarding should be: choose folder, detect installed CLI, verify login locally, launch one agent, inspect a change. Reveal account rotation, crews, voice and orchestration after that. Simplify the plan comparison around workflows while retaining existing license compatibility.

### Quiet styling sometimes hides important information

The rendered palette uses very muted descriptions and hints; its footer competes poorly with the surrounding dark canvas. The topbar truncates project/session names early. The visual hierarchy is attractive but needs stronger readability for actionable instructions and critical status. Use tooltips/full-path disclosure for truncated names, readable secondary text and visible keyboard focus. A formal contrast and screen-reader audit remains necessary; this review is not a WCAG certification.

## Architecture and remaining risks

1. **State ownership remains concentrated.** Baseline App.jsx is 2,963 lines and ipc.js is 2,308. Extract session lifecycle, identity runtime, account bindings and workspace layout behind small interfaces. Do it incrementally with regression coverage rather than rewriting the app at once.
2. **Global account overlays can conflict.** Gemini and Grok both redirect HOME/USERPROFILE; accountSlotEnv merges every selected provider overlay into one environment. The later provider can override the earlier provider's home. Provider-specific child launches need exactly one slot overlay. A general interactive shell needs an explicit strategy for launching different providers, rather than one ambiguous shared HOME.
3. **Multi-user identities are convenience isolation, not an OS security boundary.** Default CLI isolation redirects some config directories but leaves HOME unchanged. The existing PIN warning is correct: PINs do not encrypt the data. Keep this limitation visible when setting up a shared machine; avoid promising that every tool's credentials are isolated under the default mode.
4. **Unknown telemetry should stay unknown.** Health checks do not measure quota. Cached usage should show its account and observation time. Continue keeping context telemetry absent where the provider has not supplied it.
5. **Build partitioning needs cleanup.** ProfileViewer is imported both statically and dynamically, so its lazy import does not produce a separate chunk. The generated entry is about 699 KB and the terminal chunk about 631 KB, before transport compression. Measure real cold-start and memory cost before pursuing bundle refactors.
6. **The screenshot harness is useful but has limits.** It uses a stubbed IPC surface with a permissive fallback. Passing screenshots do not prove real PTY behavior, provider authentication, Windows ConPTY, safeStorage or Electron webview navigation. Add a separate packaged-app integration job for the critical ownership boundaries.

## Suggested features, in order

| Order | Feature | Why it matters / acceptance condition |
|---|---|---|
| 1 | Session account bindings and provenance | Every tab reports the exact identity, provider, slot, model and cwd used to launch it; changing a default cannot relabel another running process. |
| 2 | Recovery journal | On crash, restore workspace layout, drafts and a clearly marked last output snapshot. Offer resume only when provider capabilities support it. |
| 3 | First-run CLI doctor | One flow checks executable, version, authentication and supported resume/model flags, with a concrete fix for each failure. |
| 4 | Review-before-action change queue | Show each agent's files/diff/tests and allow selective staging or opening the diff. Separate proposal, verification and applying a change. |
| 5 | Auditable handoff cards | Carry goal, observed results, changed files, test evidence, pending work and source session/model. Let the user review the brief before launching the replacement. |
| 6 | Per-project context selection | Show exactly which instructions/files/diff are included, apply size limits and let users exclude sensitive files. Mark token estimates as estimates. |
| 7 | Provider-neutral structured activity | Add adapters only where a provider offers reliable session IDs/events. Unsupported providers retain their terminal and an honest unavailable state. |
| 8 | Flexible pane composition | Multiple simultaneous tool panes and keyboard split/tab commands, with saved layouts and predictable focus restoration. |
| 9 | Nightly release manifest and rollback | A separately versioned release pins its Sush source SHA, identifies experimental features and supports returning to a stable build. |

## Verification

Baseline: 189 tests passed across 24 files. With this review's regressions: 206 tests across 25 files. Production main, preload and renderer build successfully. The existing ProfileViewer import warning remains.

The built-renderer browser walk passed all 35 screenshot checkpoints, including the added composer, Thread and palette assertions. It uses stubbed IPC. It checks project boundaries, menus, pane routing, account/model restarts, context, structured Thread, drafts, IME input and palette dismissal. No live account login, token-bearing provider call or packaged Windows/macOS app run was performed.
